# Features roadmap — capability gaps

**Status: NOT STARTED.** Logged 2026-10-04 from a full-codebase capability review. This document tracks *missing features* — things the library doesn't do yet — as distinct from `docs/quality-roadmap.md`, which tracks *defects in what it already does*. See also `docs/features/sentinel-controls/roadmap.md` for the separately-tracked maker-checker/co-sign/break-glass initiative, which this roadmap complements but does not duplicate.

**Scope note (2026-10-04):** this is an internal library for one .NET team, not a publicly distributed product. Items aimed at onboarding *external* enterprise customers' identity infrastructure (multi-IdP support in the sense of maintained, documented integrations for several third-party vendors; SAML SSO; SCIM provisioning) are out of scope and have been moved to "Rejected / out of scope" at the end of this document rather than deleted, so the reasoning stays on record if the context ever changes.

**Vendor-lock note (2026-10-04):** OpenIddict is the *first* token authority being integrated, not the *only one that could ever be*. The team has explicitly flagged the IdentityServer4 → Duende precedent: IdentityServer4 was the de facto .NET OSS choice until its successor, Duende IdentityServer, went commercial-only, and teams that had coded directly against IdentityServer4 concepts took on migration risk or a license bill they hadn't budgeted for. The defense against repeating that isn't picking a "safer" vendor up front — it's keeping `IBedrockTokenIssuer` as the real boundary and never letting OpenIddict-specific types leak past it. See F0 below: the OpenIddict work ships as its own sibling package specifically so that if OpenIddict ever goes the same way, replacing it is "write a new `IBedrockTokenIssuer` implementation," not "rearchitect Bedrock." This is scoped to the .NET ecosystem (Keycloak and other JVM-hosted IdPs are excluded for the separate-server/cross-runtime reasons discussed below, not because non-OpenIddict .NET options are off the table).

Each phase lists the gap, why it matters, which package(s) it lands in, and a concrete starting point given the library's existing extension-point conventions (`IBedrockX` interfaces + `WithX<T>()` builder methods).

---

## Phase F0 — First-party identity-provider packaging

Bedrock already has the *right* architecture for this — it deliberately does not reimplement a standards-compliant OAuth2/OIDC authorization server itself. `IBedrockTokenIssuer` + `JwtOptions.ExternalTokenIssuer` is the seam that lets credential/MFA/session/audit management (Bedrock) sit in front of a dedicated token authority, and that seam is the thing that must stay vendor-neutral — see the vendor-lock note above. OpenIddict is simply the first concrete token authority being packaged behind it: it runs in-process as a .NET library, so the custom-grant handoff (`urn:bedrock:exchange`) is plain C#, with no cross-runtime or cross-process plugin work the way a separate-server IdP (Keycloak, Auth0) would require — that's why it's first, not why it's exclusive. This phase is about closing the gap between "documented pattern" and "shipped package" for that path, while keeping the boundary clean enough that a second implementation (Duende IdentityServer, a future OpenIddict successor, or whatever else emerges in the .NET ecosystem) is a sibling package, not a rewrite.

- [ ] **F0.1 Ship `Crestacle.Bedrock.OpenIddict` as a real package.** `docs/integrations/openiddict.md` currently hands the integrator ~250 lines of copy-paste glue: the `/connect/token` exchange controller, the assertion-signing `IBedrockTokenIssuer` implementation, the application seeder, and the DI wiring. None of this is shipped code — `grep` across every `.csproj`/`.props` in the repo confirms there is no OpenIddict package reference anywhere in `src/`. Every integrator currently reimplements the same security-sensitive assertion validation from scratch, with no code review from the library maintainers. Package this the way `Crestacle.Bedrock.Redis` and `Crestacle.Bedrock.HaveIBeenPwned` already package their integrations: a `WithOpenIddict(opts => ...)` builder extension that registers a maintained `OpenIddictBedrockTokenIssuer`, the exchange controller, and an `IHostedService` application seeder, leaving only OpenIddict's own `AddOpenIddict()` server configuration (issuer URL, flows, certificates) to the consumer. **Hard constraint: this package depends on OpenIddict; `Crestacle.Bedrock.Core` and `Crestacle.Bedrock.AspNetCore` must not.** No OpenIddict type, namespace, or assumption may leak into core — the dependency direction is `Crestacle.Bedrock.OpenIddict → IBedrockTokenIssuer (Core)`, never the reverse.
- [ ] **F0.2 Narrow the internal assertion's attack surface.** While productizing F0.1, replace the doc's bare HMAC-signed short-lived JWT assertion with one scoped specifically to the `urn:bedrock:exchange` grant (audience-pinned, single-use `jti` tracked to prevent replay) — the current sample validates signature/issuer/audience/lifetime but has no replay protection on the assertion itself between Bedrock and the token endpoint.
- [ ] **F0.3 Add an architecture test enforcing the boundary.** Extend `ArchitectureTests.cs` (or add a sibling in the Bedrock test suite — see `docs/quality-roadmap.md` D10, which already flags Bedrock's assembly stack as uncovered) with a rule asserting `Crestacle.Bedrock.Core` and `Crestacle.Bedrock.AspNetCore` carry no reference to the OpenIddict assembly. This is what actually makes the vendor-lock note enforceable rather than aspirational — a future PR that casually references an OpenIddict type from core fails CI instead of quietly calcifying the dependency.

## Phase F1 — Compliance & data rights

- [ ] **F1.1 GDPR data export / portability.** `IConsentService` and `UserCredential.Anonymize()` cover the erasure side (Article 17) but there is no "export everything you hold on me" path (Articles 15/20). Still relevant for an internal tool if any user whose data is held is an EU individual (GDPR covers employee data, not just customers). Add `IBedrockDataExportService.ExportUserDataAsync(Guid userId)` returning a structured bundle — credential metadata, sessions, known devices, consent history, audit entries, API keys (metadata only) — plus a `GET /api/bedrock/account/export` endpoint on `BedrockAccountController`. Package: `Crestacle.Bedrock.AspNetCore` + `Crestacle.Bedrock.Core` (new interface/DTO).

## Phase F2 — Abuse protection

- [ ] **F2.1 CAPTCHA extension point.** `AnomalyDetectionOptions`/`IpRateLimitOptions` exist, but there's no hook for a CAPTCHA/bot challenge on `register`, `login`, or `password-reset`. Add `ICaptchaValidator` (interface only, like `IExternalIdentityValidator`) with a `WithCaptchaValidator<T>()` builder method; ship no default implementation, document a Turnstile/hCaptcha/reCAPTCHA wiring example the way `external-idp.md` documents Google/GitHub validators. Package: `Crestacle.Bedrock.Core` (interface) + `Crestacle.Bedrock.AspNetCore` (middleware/filter wiring).
- [ ] **F2.2 Per-account rate limiting.** `IpRateLimitOptions` only throttles by IP block; a distributed low-and-slow credential-stuffing attack spread across many IPs against one account isn't throttled until the existing failed-attempt lockout trips. Add an `AccountRateLimitOptions` (failed attempts per account per rolling window, independent of IP) using the same `IBedrockCache` abstraction already backing IP rate limiting. Package: `Crestacle.Bedrock.AspNetCore`.

## Phase F3 — Operability

- [ ] **F3.1 OpenAPI/Swagger generation for Bedrock's own controllers.** None of the ~19 shipped controllers (10 Bedrock + 6 Sentinel + Sentinel.Controls once built) currently produce an OpenAPI spec consumers can load into their own Swagger UI or client generators. Add XML-doc-driven `AddOpenApi()`/Swashbuckle wiring in `AddBedrockControllers()`/`AddSentinelAspNetCore()`, gated behind an opt-in flag so it doesn't force a Swashbuckle dependency on consumers who don't want it.
- [ ] **F3.2 Webhook / external event-sink dispatcher.** `IBedrockEventPublisher` is in-process only (`DomainEvents`/`Events`) — forwarding login/lockout/anomaly/MFA events to Slack, a SIEM, or a generic webhook currently requires hand-writing a custom `IBedrockEventPublisher`. Add a built-in `WebhookEventPublisher` (HTTP POST with HMAC-signed payload, retry/backoff, dead-letter logging) as an opt-in decorator over the existing publisher pipeline. Package: new `Crestacle.Bedrock.Webhooks`, or a `Services/WebhookEventPublisher.cs` in `Crestacle.Bedrock.AspNetCore`.
- [ ] **F3.3 Admin impersonation ("login as user").** `IBedrockAdminService` covers lock/unlock/reset-MFA/reset-password/revoke-sessions/admin-change-email, but has no supported path for a support engineer to take over a user's session for debugging. Add `IBedrockAdminService.ImpersonateAsync(Guid adminId, Guid targetUserId)` issuing a short-lived, clearly-scoped token that carries an `impersonator_id` claim and is rejected by any endpoint that requires `amr` step-up — plus a mandatory audit entry. Treat this as security-sensitive from day one: narrow token lifetime, no refresh-token issuance under impersonation, audit on every request if feasible.
- [ ] **F3.4 Bulk admin operations.** Invitation, role assignment, and credential management are all single-record today. Add bulk variants (`POST /api/bedrock/account/invitations/bulk`, bulk role assignment on `UsersController`) accepting a bounded batch (e.g. ≤500 rows) with per-row success/failure reporting — not silent partial failure.

## Phase F4 — UX & localization

- [ ] **F4.1 Localization (`IStringLocalizer`).** All error messages, exception text, and any email copy are English-only. Add `IStringLocalizer`-based resource files for `BedrockErrorCodes` message templates and exception messages, following standard ASP.NET Core localization conventions, so consuming apps can supply translated resx files without forking.
- [ ] **F4.2 Reference email templates.** `NullEmailSender`/`DevEmailSender` only log; there is no starter HTML template for verification, password-reset, invitation, or security-alert emails. Ship a `Crestacle.Bedrock.AspNetCore/Resources/EmailTemplates/*.html` set (plain, themeable, documented placeholders) that a real `IEmailSender` implementation can render against, so integrators aren't writing every template from a blank file.

## Sequencing notes

- **F0.1 (first-party OpenIddict package) should come first.** It's the capability the team actually wants — becoming a real identity provider rather than rolling an independent auth solution — and the architecture already supports it; this phase is packaging and hardening existing design intent, not new design. F0.3's architecture test should land in the same PR, not later, so the boundary is enforced from the package's first commit rather than retrofitted after something has already leaked across it.
- F1.1 (data export) and F2.1 (CAPTCHA hook) are the next lowest-effort, highest-value items — both are additive interfaces following patterns the codebase already uses (`IExternalIdentityValidator`-style plug points), with no breaking changes.
- F3.3 (impersonation) should not start until `docs/quality-roadmap.md` Phase Q1–Q2 (the refresh-token/step-up TOCTOU fixes and their regression tests) are closed — impersonation adds another privileged-token path, and it should be built on token-issuance code that is already race-free and tested.

## Definition of done for this roadmap

Each item ships with: a new interface/extension point consistent with the existing `IBedrockX` + `WithX<T>()` convention, a doc page under `docs/integrations/` or `docs/` describing it the way `external-idp.md`/`openiddict.md` do, and test coverage in the same PR — not retrofitted later, per the testing gap already called out in `docs/quality-roadmap.md`.

## Rejected / out of scope

Logged with reasoning rather than deleted, in case the context changes later.

- **Maintained, documented integrations for several third-party IdPs at once (Keycloak, Auth0, Azure AD B2C, etc.).** Rejected 2026-10-04 — this is an internal library for one .NET team, not a product distributed to external integrators with varied IdPs, so there's no case for maintaining N parallel integration docs/packages. This is *not* a decision to couple permanently to OpenIddict — see the vendor-lock note at the top of this document; the actual safeguard is the `IBedrockTokenIssuer` boundary (F0), which keeps swapping to a different .NET token authority cheap whenever a concrete need arises. Note for the record on Keycloak specifically: it would also be a materially different integration shape than any in-process .NET library, since it runs as a separate JVM server — Bedrock's custom-grant pattern (`urn:bedrock:exchange`) doesn't carry over; the equivalent would be Keycloak's standard RFC 8693 token-exchange grant or stepping back to a pure Authorization-Code-flow relying-party model. That's a reason to treat it as a distinct, larger effort if it's ever needed, not a reason it's impossible.
- **SCIM provisioning (F1.2 in an earlier draft).** Rejected 2026-10-04 — SCIM exists to let *external* enterprise customers auto-provision users from their own corporate directory (Okta, Entra). An internal tool has one directory and one `Invitation`-based onboarding flow; there's no second party's IdP to sync from.
- **SAML SSO (F1.3 in an earlier draft).** Rejected 2026-10-04 — same reasoning as SCIM: SAML enterprise SSO exists to onboard external B2B customers' identity infrastructure. Not applicable to a single internal team's deployment.
